Send a task to another agent session. Always triggers the LLM in the target session.

This is the tool for starting work elsewhere. The target agent receives your message, runs, and produces a response. Use delegate when you want another agent to do something — not just to post a message.

If you only need to post a message without triggering the LLM, use reply instead.

─────────────────────────────────────────
CRITICAL: WHEN TO USE reply_to
─────────────────────────────────────────

Delegation has TWO modes controlled by the reply_to parameter:

1. WAIT FOR REPLY (no reply_to)
   - Omit reply_to parameter
   - You BLOCK until the target agent finishes
   - You receive the result inline immediately
   - Use ONLY for: quick factual questions where you need the answer right now
   - AVOID for: anything involving user interaction, complex tasks, or further delegation
   - Example: delegate({ agent: "BA", prompt: "What is 2+2?" })

2. ASYNC - EXPECT REPLY LATER (with reply_to)
   - Provide a session ID in reply_to
   - You do NOT block - you can continue with other tasks
   - The delegated agent will use reply tool to send messages back
   - The reply is USER-VISIBLE in the target session with navigation back to the delegated session
   - Use for: ALL other cases - user-facing work, complex tasks, multi-step work
   
   WHAT THE DELEGATED AGENT WILL DO:
   - They will see "Reply expected: silent" in their session context
   - They MUST use reply tool to send ANY user-facing messages back
   - The reply makes their session visible and navigable to the requester
   - They should use reply FIRST if they need user interaction (don't wait in their session)
   - The reply does NOT trigger your LLM - message just appears for you to see
   
   TWO SUB-MODES:
   
   a) REPLY TO ME (reply_to: your_session_id)
      - Provide YOUR OWN session ID (check your session context for Session ID)
      - Results come back to you
      - Example: delegate({ agent: "BA", prompt: "...", reply_to: "ses_project_owner" })
   
   b) FORWARD CHAIN (reply_to: upstream_session_id)
      - Provide a DIFFERENT session ID (e.g., who delegated to you)
      - Results skip you and go to the specified session
      - Use when: you're forwarding a delegation and don't need to see the reply
      - Check your session context for "Reply to session ID" to get the upstream session
      - Example: delegate({ agent: "BA", prompt: "...", reply_to: "ses_pandora" })

─────────────────────────────────────────
FOR MIDDLE AGENTS (forwarding delegations)
─────────────────────────────────────────

If you receive a task and need to delegate it to another agent:

OPTION 1: You want the reply to come back to YOU
- Use reply_to with YOUR session ID
- You will see the reply and can act on it
- Example: delegate({ agent: "BA", prompt: "...", reply_to: "ses_project_owner" })

OPTION 2: You want the reply to go to the ORIGINAL REQUESTER
- Use reply_to with the UPSTREAM session ID
- Check your session context for "Reply to session ID: ses_xxx"
- Pass that session ID in reply_to
- The reply skips you and goes directly to the original requester
- Example: delegate({ agent: "BA", prompt: "...", reply_to: "ses_pandora" })

IMPORTANT: If your session shows "Reply expected: silent", you are in a chain.
You can either handle the reply yourself (use your session ID) or forward it (use the upstream session ID).
   
─────────────────────────────────────────
DELEGATION PATTERNS
─────────────────────────────────────────

FORWARDING DELEGATION (common pattern):
When you receive a task but another agent should handle it:
- Keep the prompt minimal - forward what was asked, nothing more
- Do NOT add your interpretation, suggestions, or augmentation
- Do NOT ask clarifying questions on behalf of the receiving agent
- Let the receiving agent decide what they need

Example:
User asks Pandora: "Build a calculator app"
Pandora → Project Owner: "User wants to build a calculator app"
Project Owner → BA: "User wants to build a calculator app. Can you engage with the user to gather requirements?"

NOT this:
Project Owner → BA: "User wants a calculator app with basic operations, scientific functions, and a modern UI. Please gather detailed requirements including..."

─────────────────────────────────────────
SESSION TYPES
─────────────────────────────────────────

worker   — short-lived, one task, auto-closes when done (max 500 messages)
scope    — project-anchored, preserves context, auto-archives when done
role     — persistent ongoing session for a specific agent role (BA, Architect, etc.)
scratchpad — throwaway, auto-deletes after 6h inactivity (max 100 messages)

─────────────────────────────────────────
SESSION TARGETING — pick one approach
─────────────────────────────────────────

1. NEW SESSION:      agent + session_type + title  →  creates a child session
2. EXISTING SESSION: session_id                    →  targets a specific session
3. AGENT MAIN:       agent only                    →  uses or creates the agent's main session

─────────────────────────────────────────
RULES
─────────────────────────────────────────

- Always provide a title when creating a new session.
- After fire-and-forget (wait: false), your turn is complete. Do not poll or resend.
- Do not delegate to your own session.
- reply_to is for silent reply only. If you want the origin LLM triggered, the receiving
  agent must call delegate back — you cannot force this from the calling side.
- Each agent only delegates to agents it knows about. Do not invent agent names.
