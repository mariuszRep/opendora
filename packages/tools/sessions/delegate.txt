Send a task to another agent session. Always triggers the LLM in the target session.

This is the tool for starting work elsewhere. The target agent receives your message, runs, and produces a response. Use delegate when you want another agent to do something — not just to post a message.

If you only need to post a message without triggering the LLM, use reply instead.

─────────────────────────────────────────
REPLY MODES — choose one when delegating
─────────────────────────────────────────

1. WAIT (synchronous)
   wait: true
   You block until the target agent finishes. You receive the result inline.
   Use for: quick factual questions where the answer drives your immediate next step.
   Avoid for: anything involving user interaction or further delegation — it will deadlock.

2. FIRE-AND-FORGET (automatic reply routing)
   wait: false
   Default behavior: replies automatically route to whoever delegated to you.
   - If you're responding to a user request, replies come back to you
   - If you're forwarding a delegation, replies go to your caller (chain preserved)
   Use for: most async tasks, user-facing work, multi-hop delegations
   
3. REDIRECT REPLY (override routing)
   wait: false, reply_to: <session_id>
   Override default routing to send replies to a specific session.
   Use for: forwarding delegation but wanting replies to go to original requester
   Example: Project Owner forwards to BA, sets reply_to to Pandora's session
   
─────────────────────────────────────────
DELEGATION PATTERNS
─────────────────────────────────────────

FORWARDING DELEGATION (common pattern):
When you receive a task but another agent should handle it:
- Keep the prompt minimal - forward what was asked, nothing more
- Do NOT add your interpretation, suggestions, or augmentation
- Do NOT ask clarifying questions on behalf of the receiving agent
- Let the receiving agent decide what they need

Example:
User asks Pandora: "Build a calculator app"
Pandora → Project Owner: "User wants to build a calculator app"
Project Owner → BA: "User wants to build a calculator app. Can you engage with the user to gather requirements?"

NOT this:
Project Owner → BA: "User wants a calculator app with basic operations, scientific functions, and a modern UI. Please gather detailed requirements including..."

─────────────────────────────────────────
SESSION TYPES
─────────────────────────────────────────

worker   — short-lived, one task, auto-closes when done (max 500 messages)
scope    — project-anchored, preserves context, auto-archives when done
role     — persistent ongoing session for a specific agent role (BA, Architect, etc.)
scratchpad — throwaway, auto-deletes after 6h inactivity (max 100 messages)

─────────────────────────────────────────
SESSION TARGETING — pick one approach
─────────────────────────────────────────

1. NEW SESSION:      agent + session_type + title  →  creates a child session
2. EXISTING SESSION: session_id                    →  targets a specific session
3. AGENT MAIN:       agent only                    →  uses or creates the agent's main session

─────────────────────────────────────────
RULES
─────────────────────────────────────────

- Always provide a title when creating a new session.
- After fire-and-forget (wait: false), your turn is complete. Do not poll or resend.
- Do not delegate to your own session.
- reply_to is for silent reply only. If you want the origin LLM triggered, the receiving
  agent must call delegate back — you cannot force this from the calling side.
- Each agent only delegates to agents it knows about. Do not invent agent names.
