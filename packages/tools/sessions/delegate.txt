Send a task to another agent session. Always triggers the LLM in the target session.

Use delegate when you want another agent to do something — not just to post a message.
If you only need to post a message without triggering the LLM, use reply instead.

─────────────────────────────────────────
BEFORE YOU DELEGATE — REASONING ORDER
─────────────────────────────────────────

Before calling delegate, reason in this order:

1. What is the request?
2. Did it come from the user directly, or was it delegated to you from upstream?
3. Is there a better-suited available agent for this work?
4. If yes — delegate rather than doing the work yourself.
5. If delegating — do you need the result back yourself to make your own next decision?
6. If NO — preserve and forward the current return path (the upstream reply_to) rather
   than replacing it with your own session ID.
7. If the downstream work involves interacting with the requester — route it so the
   downstream agent can surface directly into the upstream visible conversation.

─────────────────────────────────────────
CHOOSING reply_to — THE ROUTING CONTRACT
─────────────────────────────────────────

reply_to decides where user-facing results and questions will surface.
Choosing reply_to is part of the delegation decision, not an afterthought.

DEFAULT — forward the upstream return path:
- If you received this task with a reply_to in your session context, and you are
  only forwarding it to a better-suited agent, pass that same upstream session ID
  as reply_to.
- The downstream agent will surface directly into the visible conversation that
  originally requested the work.
- Check your session context for "Reply to session ID: ses_xxx" — that is the value to forward.

EXCEPTION — route to yourself:
- Only set reply_to to your own session ID if you genuinely need the result back
  before you can make your next decision.
- Do not route to yourself by default. Routing results through yourself when you
  do not need them adds unnecessary hops and breaks visibility.

TWO MODES controlled by whether reply_to is provided:

1. WAIT FOR REPLY (no reply_to)
   - You BLOCK until the target agent finishes and receive the result inline.
   - Use ONLY for quick factual lookups where you need the answer right now.
   - AVOID for anything involving user interaction, complex tasks, or further delegation.

2. ASYNC WITH RETURN PATH (with reply_to)
   - You do NOT block. The delegated agent uses reply to send messages back.
   - The reply is USER-VISIBLE in the reply_to session with navigation back to the
     delegated session.
   - Use for ALL other cases — user-facing work, interactive tasks, multi-step work.
   - The delegated agent will see "Reply expected: silent" in their session context
     and MUST use reply for any user-facing message.

─────────────────────────────────────────
WRITING THE DELEGATION PROMPT
─────────────────────────────────────────

Delegation prompts must be minimal and role-respecting:

- Pass the request and any essential context.
- Do NOT tell the receiving specialist how to perform their specialty.
- Do NOT add step-by-step instructions for how they should do their job.
- Do NOT ask clarifying questions on behalf of the receiving agent.
- Let the receiving agent decide how to perform their role.

GOOD:
  "The user wants to build a calculator app. Please engage with the user to gather requirements."

BAD:
  "The user wants a calculator app. Please gather detailed requirements. Ask one question at a
   time. Focus on calculator type, platform, features, UI, and technical constraints."
  (The BA knows how to gather requirements — do not instruct them on their own method.)

GOOD (reply_to routing):
  Project Owner receives a task from Pandora (reply_to: ses_pandora).
  Project Owner delegates to BA and forwards the upstream return path:
  delegate({ agent: "BA", prompt: "...", reply_to: "ses_pandora" })
  → BA surfaces replies directly into Pandora's conversation.

BAD (reply_to routing):
  Project Owner replaces the upstream reply_to with their own session:
  delegate({ agent: "BA", prompt: "...", reply_to: "ses_project_owner" })
  → BA replies to Project Owner instead of the original visible conversation.
  → The requester cannot see the BA's questions or results without Project Owner relaying them.

─────────────────────────────────────────
SESSION TYPES
─────────────────────────────────────────

worker     — short-lived, one task, auto-closes when done (max 500 messages)
scope      — project-anchored, preserves context, auto-archives when done
role       — persistent ongoing session for a specific agent role (BA, Architect, etc.)
scratchpad — throwaway, auto-deletes after 6h inactivity (max 100 messages)

─────────────────────────────────────────
SESSION TARGETING — pick one approach
─────────────────────────────────────────

1. NEW SESSION:      agent + session_type + title  →  creates a child session
2. EXISTING SESSION: session_id                    →  targets a specific session
3. AGENT MAIN:       agent only                    →  uses or creates the agent's main session

─────────────────────────────────────────
RULES
─────────────────────────────────────────

- Always provide a title when creating a new session.
- After async delegation (reply_to provided), your turn is complete. Do not poll or resend.
- Do not delegate to your own session.
- Delegation is task transfer AND return-path choice. Both decisions matter.
- When forwarding a task, forward the upstream reply_to by default.
  Only override it with your own session ID if you need the result for your next step.
- reply_to delivers a silent message. To trigger the recipient's LLM, they must call
  delegate back — you cannot force this from the calling side.
- Each agent only delegates to agents it knows about. Do not invent agent names.
